The problem

Network design still starts by hand

Engineers and students who prototype networks in GNS3 place every device, wire every interface, plan the addressing, and write the routing and security configuration themselves. It is slow and easy to get wrong, especially past a handful of nodes.

Existing automation tools such as NAPALM, Netmiko, and Terraform manage configuration for networks that already exist. None of them covers the step before that: going from an idea to a topology.

StructuraNet AI covers that step. You describe what you want, refine it in conversation, review it on a canvas, and export a portable GNS3 project with startup configurations for every device.

Design principle

The LLM proposes. Python decides.

A language model is good at reading intent and sketching a design. It is unreliable at port numbers, hardware limits, and file formats.

So the engine gives the model a narrow job and surrounds it with deterministic code. Every model output passes through repair, schema validation, and merge rules before anything is written to disk.

  1. Intent routing

    Deterministic shortcuts and a heuristic classifier answer simple requests without calling the model. Design requests enter a tool loop of up to 6 rounds.

    CODE

  2. Topology synthesis

    The prompt carries the user's available hardware, per-device link limits, a six-step build algorithm, and 12 mandatory rules. The model returns JSON nodes and connections.

    LLM

  3. Auto-repair

    Three fixes run before validation: remove duplicate links, add a switch behind single-port devices, and bridge disconnected parts of the graph.

    CODE

  4. Validate and retry

    Pydantic models check unique IDs, real endpoints, port limits, and full connectivity. Failures go back to the model as feedback, up to 3 attempts.

    CODE

  5. Ports and hardware

    Ports are assigned by code, never by the model. Hardware properties for Dynamips, IOU, and QEMU nodes come from a 45-device catalog.

    CODE

  6. Configuration generation

    A readable configuration brief and seven Layer 3 rules guide the model as it writes Cisco IOS configs for each device.

    LLM

  7. Three-gate safe merge

    Model-written configs can only fill software fields. Hardware and metadata set by code cannot be overwritten.

    CODE

  8. Export and validate

    A 12-stage exporter writes a portable .gns3project archive with deterministic UUIDs. Then 11 structural checks run on that archive.

    CODE
Three-gate safe merge

Configs written by the model can't break the hardware.

Phase 2 asks the model for device configurations, then merges them into a topology that deterministic code already built. Each key the model returns must pass three gates, and every rejection is logged with a reason.

Gate 1

Whitelist

Only five software keys are accepted, such as startup_config_content. Anything else, including internal _metadata, is dropped.

Gate 2

No overwrite

A value that is already set is never replaced. Empty placeholders are the only exception.

Gate 3

Type check

Each value must have the expected type. Config text must be a string, and the environment must be a dict or string.

# structranet/ai/config_agent.py · safe_merge_configs (excerpt)
for key, value in config.items():
    if key.startswith("_"):
        continue                                   # internal metadata is never writable
    if key not in SOFTWARE_CONFIG_KEYS:          # Gate 1: whitelist
        reject(node_id, key, "not in whitelist"); continue
    if properties.get(key) not in ("", {}, [], None):  # Gate 2: no overwrite
        reject(node_id, key, "already set"); continue
    if not isinstance(value, ALLOWED_VALUE_TYPES.get(key, (str,))):  # Gate 3: type
        reject(node_id, key, "wrong type"); continue
    properties[key] = value

Condensed from the repository. The full function also skips configs for unknown node IDs and counts merged keys.

Node.js ↔ Python

One warm worker, one simple protocol

The first version started a new Python process for every request, which re-imported the OpenAI SDK, the device catalog, and the validators each time.

The engine now runs as a persistent worker. It loads once and then takes commands from the Express backend as newline-delimited JSON. Every message carries a request ID, so progress events stream back to the browser over SSE while the work runs.

// request  (Node.js → stdin)
{"id": "7f3c…", "command": "generate", "args": {…}}
// event    (stdout → Node.js → SSE)
{"id": "7f3c…", "event": "phase_change", "data": {…}}
// response (stdout → Node.js)
{"id": "7f3c…", "ok": true, "result": {…}}

Security profiles

Hardening that changes the design

The profile shapes both phases: it adds rules to the topology prompt and sets how deep the generated IOS hardening goes.

Tier 1

None

No security constraints. Useful for quick labs and teaching basics.

Tier 2

Basic

  • SSH v2
  • AAA local auth
  • NTP
  • Syslog
  • Login block-for
  • No SNMP communities
Tier 3

Enterprise

  • Zone-based firewall
  • Anti-spoofing ACLs
  • OSPF MD5
  • HSRP
  • SNMPv3
  • DHCP snooping
  • Dynamic ARP inspection
  • Port security
  • uRPF
Export validation

Evidence

What we verified, and what we didn't

The thesis reports mechanisms and executed tests. It does not claim success rates or speedups that were never benchmarked.

Verified

Executed and checked

  • Golden export test: a minimal topology exports and passes all 11 structural checks. I re-ran it on the public repository in October 2026, and it passes.
  • Five golden export cases were recorded as passing in the thesis on 15 July 2026.
  • Safe-merge audit: injected attempts to overwrite the platform, metadata, and existing configs were all rejected by the right gate.
  • Validator error injection: removing required keys, pointing links at missing ports, and invalid VLANs each triggered the expected severity.
  • Generated projects imported into GNS3, as shown in the screenshots above.
Not yet measured

Open work, stated plainly

  • How often auto-repair fires and how many retries a typical request needs. This needs a fixed prompt set and a pinned model.
  • The latency gain from the persistent worker over one process per request.
  • Intent classification accuracy on a labeled corpus.
  • Generated Cisco configs are a starting point. They are not certified production-ready.
